# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

`files` is an Ada 2022 desktop file manager. Core logic (~92K lines in `src/`) is platform-agnostic; rendering uses Vulkan + GLFW + `textrender`. Linux is the only production-validated platform.

## Build, test, verify

Built with Alire (`alr`), which wraps GNAT and the `.gpr` project files.
Use Alire GNAT 15 only. The development, release, tests, and tools
manifests pin `gnat_native = "=15.2.1"`. Validate with
`alr exec -- gnatls --version`.
Do not run plain system `gnat*`, `gnatmake`, `gnatls`, `gnatprove`, or
`gprbuild` in this workspace; use `alr exec -- ...` for compiler and builder
commands.

- `alr build` — compile the main app. Style is checked at compile time, so a clean build also passes style.
- `cd tests && alr test` — run the AUnit suite (it lives in `tests/`, with its own `alire.toml`/`.gpr`, and builds before it runs). `alr test` from the repo root runs *no tests*: with no test action defined there it falls back to a release build and reports success.
- check_all — `tools/files_check_all.gpr` builds the `check_all` utility for file-format validation and full GNAT compiles.
- `bin/files [PATH...]` — run the built app (defaults to home dir). `--runtime-smoke` / `--live-smoke` for headless/live validation (needs Vulkan + display).

Verify non-trivial changes with the full chain: `alr build` → `cd tests && alr test` → check_all. Or run `/verify-deep`.

## Dependencies need sibling checkouts

`alire.toml` pins the sibling runtime crates (`i18n`, `messages`, `hostkit`,
`humanize`, `textrender`, `zlib`, `cryptolib`, `guikit`, and `a11y`) to
relative paths (`../i18n`, etc.; `a11y` lives in `../a11ykit`), not published
crates. The tooling crate pins
`project_tools` under `tools/alire.toml`; the runtime crate should not depend
on it. Builds fail unless those sibling directories exist next to this repo.

## Code style (enforced by the compiler — not just convention)

These come from `config/files_config.gpr` and will **fail the build** if violated:

- 3-space indentation (`-gnaty3`)
- 120-character max line length (`-gnatyM120`) — a hard limit
- Full GNAT style checks (`-gnatya`, casing, layout, spacing) and full warnings (`-gnatwa`)
- UTF-8 source encoding (`-gnatW8`), Ada 2022

## Platform-specific sources

Files uses one source list on every OS; platform-specific services live in the
`hostkit` sibling. Only Linux is validated locally; treat Windows/macOS bindings
as present-but-unverified.

## Rendering and UI components

Two-phase render, each phase a subunit of `Files.Rendering`: `Files.Model` → `Build_Snapshot` (an immutable `View_Snapshot`, built in place by `Build_Snapshot_Into` in `files-rendering-build_snapshot_into.adb`) → `Build_Frame_Commands` (a `Frame_Commands` draw list, in `files-rendering-build_frame_commands.adb`) → Vulkan. Input flows back the other way: `Files.Events` (translate to an `Input_Action`, declared in `Files.Input_Actions`) → `Files.Interaction` (dispatch) → `Files.Controller` (apply to the model). Keep `files-rendering.adb` itself from regrowing — move any new large subprogram body into its own subunit. `Files.Rendering` holds the snapshot and frame types; layout records and their `Calculate_*` functions live in `Files.Rendering.Layouts` (shared with `Hit`, `Events` and the window layer), the metrics they build on (paddings, column widths, saturating arithmetic, text wrapping) in the private child `Files.Rendering.Geometry`, what is shown as text or colour (glyphs, permission words, info-pane field values, label colours) in the private child `Files.Rendering.Labels` (times, sizes and numbers come from `Files.Rendering.Display_Text`), and the text renderer pool plus per-window glyph cache in `Files.Rendering.Text`. The rule between the first two: anything a drawing and a hit test both resolve against (menu rows, details header and columns, toolbar buttons, the path field's star offset) is `Layouts'`; `Geometry` does not depend on `Layouts`. A frame reads the model and changes none of it: check_all's `Check_Rendering_Model_Reads` derives every `Files.Model` mutator (a subprogram taking the `Window_Model` `in out`) from the model's specs and refuses any in a `files-rendering*` unit; a `files-interaction*` unit is refused more, any subprogram outside `Files.Controller` that takes the model `in out` (an operation, a refresh, an overlay's edit): a dispatch changes the model only through the controller; the window's input dispatch — its pointer gestures (`files-application-windows-gestures*`), its keyboard dispatch (`handle_keyboard`, `fire_key`) and the selection's reveal (`reveal_selection`) — is refused the same, and places a region (`Controller.Scroll_To`, `Reveal_Selection`), selects a marquee's rows, notes a held key's repeat (`Note_Key_Repeat`, through `Interaction.Handle_Key`'s `Repeated`) and bands the items (`Sync_Grouping`) through the controller. A leading child of `Files` (`Model.`, `Refresh.`, `Operations.`) is read as `Files.` that name, and a use clause or renaming of a unit owning a refused subprogram is refused too. The window chrome (toolbar and bottom bar, paddings, default window size) is in `Layouts` too; there is no separate `Files.UI`. `Layouts`' spec is grouped by region (shared pieces, main view, toolbar, bottom bar, side panels, overlays, frame); what lies inside a region has its own public child: `Layouts.Menus` (context and sort menu rows), `Layouts.Details` (the details header, column separators and header sorts), `Layouts.Tree` (tree rows and pick buttons) and `Layouts.Dialogs` (the popups and dialogs that are no region of the frame: Quick Look, the label picker, the root selector's rows, the paste-conflict dialog, paste progress). The parent keeps every frame region and what its own bodies place by (`Compute_Detail_Columns`, in its private part).

Reusable UI pieces are black-box components in `../guikit` (`Guikit.Command_Palette`, `Settings_Panel`, `Segmented`, `Item_Grid`, `List_Panel`, `Menu_Tree`, `Widgets`); files also delegates shared non-visual helpers there (`Guikit.Utf8.Editing`, `Guikit.Input.Mouse_Buttons`, `Guikit.Fonts`). files owns the domain (selection, rename, icon assets, localization) and maps it to each component's neutral inputs. **Whether a component is stateful fixes how it integrates — do not re-decide per component:**

- **Stateless render helpers** (`Segmented`, `Item_Grid`, `List_Panel`, `Menu_Tree`, `Widgets`) are called from inside `Build_Frame_Commands`, driven by the snapshot. Prefer this.
- **Stateful overlays** (`Command_Palette`, `Settings_Panel` — they hold query/scroll/focus state across frames) cannot pass through the immutable snapshot: their instance lives in the `Window_Model`, `Files.Overlays` draws them from that state, and the window layer merges the result into the cached frame: `files-application-windows-render_window-present_frame.adb` calls `Append_Overlay`, which is defined in `files-application-windows.adb`.

`Files.Model` keeps the `Window_Model` record and the cross-cutting operations (navigation, focus, text caret, overlay stack); each concern is a public child that sees the private record: one per overlay (`Command_Palette`, `Settings_Pane`, `Root_Selector`, `Sort_Menu`, `Context_Menu`, `Label_Picker`, `Quick_Look`, `Tree_Panel`, `Pasting`, `Clipboard`) and `Selection` (with its own child `Selection.Type_Ahead`), `History` (undo/redo), `Rename`, `Filtering` (filter text, search scope and results), `Recent` (the opened-item and path-move queues the controller persists — `Controller.Finish_Dispatch` after an input, `Controller.Follow_Path_Moves` after a background job — and whether the recent view is shown), `Ownership_Input`, `Info_Pane`, `Creation` (the new item's temporary row), `Folder_Sizes`, `Status_Samples` and `Jobs` (the foreground/background job state: whether helpers run, which modal job runs and ending it). The overlays stack in one order, `Files.UI_Types.Overlay_Stack`: the model's `Topmost_Overlay`, the keyboard (`Controller.Handle_Key` offers keys to the top overlay only) and the pointer (`Events` routes clicks through `Rendering.Topmost_Overlay_Position`) all follow it. Callers name the child (`Files.Model.Selection.Select_Visible`). **Model children never `with` each other.** What the parent or another child needs from a concern — an overlay's close/reset (so `Close_Overlay` and `Claim_Overlay_Input` reach it), the selection queries the overlays read — lives in the private child `Files.Model.Support`, and the concern's public subprogram renames it; everything only its own child uses stays in that child's body.

The model tells a view what went stale through revision counters, each moved by one helper and never by hand — in `Files.Model.Support`, except `Settings_Revision` (`Note_Settings_Changed`) and `View_Incarnation` (`Set_Current_Path`), which the parent body moves: `Touch` (Revision and Rows — a full row rebuild), `Touch_Rename`, `Touch_Selection`, `Touch_Header` (Revision alone — a header-only snapshot build), `Touch_Info` (the info pane's rows), `Note_Folder_Sizes`, `Touch_Overlay` (only the overlays drawn from the model: the palette and the settings pane; the snapshot stays), `Touch_Scroll` and `Touch_Listing` (stale background reads). Every counter wraps (`Bumped`) and is compared only for equality. A mutator calls the narrowest helper that covers what it changed; the table in `files-model.ads` says which helper moves which counter and who reads it.

## Non-UI layering

Below the UI the units stack one way:

- `Files.IO.*` (bounded/lease/durable streams, `IO.Errors`)
- → `Files.Jobs.*` (job records' wire primitives, context journal, process sessions, transports, startup recovery; reaches nothing from `File_System` up, and calls back into it only through the `Jobs.Storage` port — check_all's `Check_Job_Layer` enforces this; it translates nothing either: `Jobs.Scavenger` takes its report text from the caller)
- → `Files.File_System`. Listings and searches take the classification maps (`File_Types.Classification`) and `Types.Listing_Options`, not the settings record: nothing `File_System` reaches, however indirectly, is `Files.Settings` (check_all's `Check_File_System_Closure`). `File_Types` owns the map type, the built-in maps (`Default_Classification`) and the lookups; `Settings.Classification_Of` builds one from a settings model. Its value types live in `Files.File_System_Types`, where clients name them — `File_System` does not re-export them. The parent's public spec holds the result types, listing, the core mutations and the cancel-versus-failure rule (`Job_Cancelled`, `Says_Only_Stopped`); each further concern is a public child that declares and implements its own API (its subunits are `separate` of the child, not of the parent): `Roots`, `Search` (with `Recursive_Search_Result`), `Transfer` (drop/paste plans and imports, a destination's naming rules `Name_Rules_Of`, tree copies, staged publication; `Execute_Drop_Import` in its private part), `Recovery_Registry`, `Trash` (the home, volume and native trashes, whose backends and test hooks sit in its private part) and `Permissions` (whose ownership test hook sits in its private part); the trash backend and native-request types are `Trash`'s, the mount-point rule `Roots`'. The public child `Thumbnails` writes and reads the thumbnail cache. The parent's private part keeps only what the parent and several children share (`Entry_Is_Hidden`, `Path_Is_Within`, checksums, the copy, restore, delete and sweep test hooks); a child's private declarations reach the suite through a `*.Testing` child of that child. The private children `Support` (moving and removing entries, source snapshots, staging, listing a folder, files' data folder) and `Copying` (the copy engine: `Copy_To_New_Path`, `Publish_From_Stage`, the hard-link journal) are what those share, and the private child `Recovery` is the crash-safe replace (preserving an entry aside, putting it back, the recovery registry's payloads); the private child `Content_Info` sniffs what an item's content says for the info pane (the parent's `Extra_Info_Of` answers through it), and `Account_Names` memoizes the names behind owner and group ids. `Files.Images` (the PNG and NetPBM decoders) sits beside `Jobs` on the leaf units and `IO`; `File_System` uses it.
- → `Files.Undo.*`, `Files.Model`, `Files.Folder_Size` (the folder-size values and the session the model holds as data; its child `Folder_Size.Measuring` is the helper job that measures them), `Files.Transfer_Jobs` (the paste copy/move helper job; the model holds its session as a plain `Jobs.Process.Session`), `Files.Paste_States` (a paste's resolved actions and progress) and `Files.Job_Payloads` (settings, listing and operation-result records the job helpers carry, over `Files.Operation_Results`, the result records themselves, which use only `Settings` and `Types`)
- → `Files.Refresh` (`Reinstall_Listing`, the one way a view read again is installed — a folder, the Recent view or search results, read again in place after an operation, by the background listing or by an operation helper's snapshot, and a new search's results — keeping the selection, scroll, info pane and Quick Look, and ending as every listing shown does (`Settle_Listed`, which `Operations.Support`'s `Load_And_Show` ends with too): the watch signature, missing thumbnails owed to a background listing, its error line (a search's notice, or an error kept from before the read) and the selected item's details; the Recent view shown is listed again only here (`Model.Replace_Recent_Items`; `Model.Navigate_Recent` only enters it, and the Navigate Recent command, a Refresh or Clear Recent in the view reload it through `Operations.Support.Reload_Current_Directory`); every search a view shows comes from `File_System.Search.Search_Folder` (by scope, with its notice and signature), in the window or in a helper; the background listing — or, while the window shows search results and the caller asks for it (`Start`'s `Search_Again`, as every operation's reload does), the same search again, for the query the results answer (`Model.Filtering.Search_Query`, noted with them; what is typed in the field since does not count — typing makes no read stale, and over results it changes only the field), so no search runs on the window's thread and no listing passes for results; an operation says what it says before its reload is scheduled (`Operations.Support.Reload_Saying`), since the error line moving after a background read began makes the read stale; an operation helper that read the results again after acting (Trash, Delete, Restore, Empty Trash, Undo, Redo) has its results shown, not searched a second time; a reload selects the item an operation made or changed by its full path (`Select_Path`, also carried back from a helper), as results may list two items of one name; new results settle a listing owed to the folder — incl. `Ensure_Selected_Item_Extra` and `Load_Recent_Items`; its child `Refresh.Watch` is the folder watch: the watch helper, its session and the pacing of the re-reads it asks for)
- → `Files.Operations`. The parent keeps what several concerns share (`Refresh`, `Refresh_If_Changed`, `Apply_Ui_State`, `Start_At_Folder` for a new window, the refusals); each concern is a public child — `Navigation`, `Opening`, `Editing` (create, duplicate, link, rename, thumbnails), `Archives`, `Trash`, `Paste`, `Metadata` (permissions and owner), `History` (undo/redo) and `Tree` — and the private child `Support` holds what they share (incl. the trash-folder checks, and the one way a view moves to a folder, `Load_And_Show`: the folder read, the caller's install (navigation, the typed path, Back and Forward — read before the window moves, so a failed one changes nothing — a new window), then the trash flag, watch signature, error line, and missing thumbnails owed to a background listing the window's poll starts); `Undo_Recording` records the undo history, the growing entry of a batch (`Progressive_Undo`, `Checkpoint_Undo`, `Finish_Undo`) included, and `Archives.Writing` writes archives. A child's private declarations reach the suite through a `*.Testing` child of that child (tests/tests/src); test-only helpers live there too, never in a production spec.
- → `Files.Job_Drivers.*` (they run `Operations`).

Settings are domain data below all of this: `Files.Settings` (the model, its text format, the view mutators; it uses only `File_Types`, `Icon_Themes` and the leaf units) with `Settings.Storage` (where the file lives, `Configured_Settings_Path`: `FILES_SETTINGS`, then `XDG_CONFIG_HOME` on every host, then an existing `~/.config/files/settings.conf`, then the host's configuration folder; reading and writing it, taking in another process's changes first, and deciding every change, `Decide_Commit`), `Settings.Drafts` (the settings pane's editable draft) and `Settings.Path_References` (favorites, recent paths and colour labels: matching a path against the stored ones, the `Path_Index` a caller asking about many paths builds once, and following the items moved or removed: `Follow_Path_Moves` takes a window's queued moves in one pass over the stored paths, matching each path's heads by key). Paths match without regard to case where the volume folds names — always on Windows, per volume on macOS (a volume query, cached briefly; `Path_References` asks it through Hostkit) — and exactly elsewhere; a caller asking about one folder's items decides once for the folder (`Folding_In`, a `Text_Case.Path_Folding` the window samples into `Model.Status_Samples.Name_Folding`) and passes it to `Index_Paths`, which keys the stored paths by the same rule, so matching rows asks no volume. `Files.Commands` is the command catalog (ids, names, shortcuts, and the keymap's rules: `Rebind` binds a command to a chord in a `Keymap` — a conflict with another primary, a chord taken from a built-in secondary, the default clearing the override — so the settings pane's glue only parses its field keys), with `Commands.Keymap_Settings` reading a `Commands.Keymap` from the settings' shortcuts — bound by the keymap's rules (`Commands.Rebind`), so overrides merged from two processes never share a chord and one equal to the default is none — and back, and putting the settings' in force as the live keymap, `Commands.Context_Menus` (which commands each context menu shows), `Commands.Overlay_Buttons` (which command buttons an overlay on top answers: `Events.Translate_Click` emits them and `Interaction` admits only them while it is on top) and `Commands.Status` (whether a command can run, read from the model alone — what the host offers too, as the window sampled it; it reaches no `File_System`). `Settings.Storage` writes exactly the settings it is handed; `Files.Controller` (its private `Commit_Settings` and `Take_In_Settings`, and `Persist_Settings`) puts accepted settings' shortcuts in force (the settings pane edits them in its draft only, so a refused rebind changes no key) and a rebind taken in from the file, both through one private step (`Follow_Shortcuts`), and otherwise only applies a settings outcome to a window — its error line, the open pane (whose draft merges an outside change per setting and per command's shortcuts, `Overlays.Settings_Form.Refresh_Draft`, its own unsaved shortcut edits bound again over what is in force so an edit whose chord the outside change took gives way with the pane's conflict message), the palette, the tree and the listing (read again only for the hidden filter or the type and icon maps, search results taking them in place, folder sizes kept — a settings-pane save and the Toggle Hidden Files command follow the same rule, `Follow_Listing_Settings`). Every settings edit is the controller's (the path bar's star `Toggle_Folder_Favorite`, `Label_Selection`, `Set_Font_Size`, `Resize_Column`, `Reorder_Column`, `Persist_UI_State` for the view mode, sort and info pane a command changed, `Finish_Dispatch` (the recent opens, with the selected item's extra info) and `Follow_Path_Moves`, `Adopt_Shared_Settings` for another window's, `Remember_Window_Size`, `Show_Theme` for a smoke scenario's theme, the settings commands); `Interaction` and the window layer translate the input and dispatch it. Every change takes one decision (`Decide_Commit`, in the controller's private `Apply_Unsaved`): `Commit_Settings` (private: every edit enters through one of the entries above) writes the file at once; a change made while dragging, wheeling or holding a key (a column width, a wheel zoom, a held step) is put in force by the same decision and written once it ends (`Persist_Settings`, `Persist_Held_Settings`). `Files.Quick_Look` (preview content) is domain over `Items` and the leaf units; its child `Quick_Look.Preparation`, which reads the previewed file, sits at the `File_System` level (it uses `File_System` and `File_System.Thumbnails`; `Refresh` and the controller call it). `Files.Paste` (conflict names and folding) is a pure leaf: it asks no filesystem, and a destination's naming rules come from `File_System.Transfer.Name_Rules_Of`. `Files.Items` (the directory item record, over `Types` and `Extra_Info`) and `Files.Item_Lists` (sorting and classifying items, over `Items` and `File_Types`) sit just below `File_System`, which uses both; `Files.Grouping` (which band an item falls in) is leaf-level and used by the model and the snapshot. `Files.Resources` (finding the shipped data) sits on `IO`; `Files.Localization` (the catalogs) on `Resources`, and `Files.Root_Labels` and `Files.Desktop_Applications` (installed applications for Open With; it also reads `Settings.Open_Actions`; the application record the model holds is the leaf `Desktop_Application_Types`) on `Localization`. `Files.Fonts` (on `Images`; the window layer, `Rendering.Text` and `Extension_Labels` load faces through it) and `Files.Application.Icon_Assets` (on `Resources` and `Icon_Themes`) serve the drawing; `Files.Drop_Events` (an OS drop translated to an import mode) is used by the window layer, `Interaction` and the controller. A dispatch reaches nothing below the controller and changes the model only through it: `Interaction` reads the model and hands the controller the input's own values (a paste-conflict button is `Handle_Conflict_Button`'s `Input_Actions` kind; a right-click `Handle_Right_Click`, a palette click `Click_Palette_Row`, a marquee's rows `Select_Marquee_Rows`, a chosen menu row `Close_Context_Menu`) and ends with `Controller.Finish_Dispatch` — every dispatch does: a key (a zoom chord included), typed text, an input action, a drop.

Leaf units every layer may use: `Types` (domain types only, and the `String_Vectors` and exact `String_Sets` every layer shares), `Text_Case` (with `Path_Folding`, how paths match by case), `Name_Parts`, `Text_Basics`, `Text_Encoding`, `Preference_Types`, `UI_Types`, `Command_Reasons` (why a command is disabled, and its message key), `File_System_Types`, `Path_Checks`, `Protocol_Names`, `Hex_Text`, `Timing`, `Environment`, `Diagnostics`, `File_Identities`, `Extra_Info`, `Desktop_Application_Types`, `Leaf_Names`, `Folder_Tree` and `Breadcrumbs`.

A helper with a single client family is that family's child, not a top-level unit: `Overlays.Command_Palette` and `Overlays.Settings_Form` (the stateful overlays' domain glue), `Controller.Operation_Commands`, `Controller.Clipboard_Text` (the Copy Path text), `Rendering.Display_Text` (times, sizes and numbers as text; `Rendering.Labels` keeps glyphs, command names, permissions and the info pane's fields), `File_System.Digests` and `File_System.Trash.Info_Codec`, `Model.Selection.Type_Ahead`, `Operations.Archives.Writing` (`Extension_Labels` stays top-level: it rasterizes badge glyphs through raw atlas memory, which the rendering family's no-`System` guardrail rightly refuses); the controller runs pure model commands in its own `Execute_Pure_Command`. Window-layer units used only by `Files.Application.Windows` are `Files.Application.*` children (`Window_Policy`, `Snapshot_Slots`, `Accessibility`, the per-frame `Window_Polls`, and the off-thread readers `Extra_Info_Reader`, `Preview_Decoder` and their `Background_Slots`, …); so are the window layer's other single-client helpers, `Settings_Keys` (the settings a snapshot is built from, captured so the window can tell whether its cached snapshot still shows them; `Snapshot_Slots` is its one client) and `Icon_Assets` (the icon definitions served to `Guikit.Draw`, installed at startup); `Snapshot_Policy` stays top-level because it is `Pure`.

## Localization

`share/files.catalog` and `share/locales/files-*.catalog` are plain-text `key=value` catalogs (default locale at top, keys namespaced like `en.command.view.small`). Generated/converted by the `cldr_to_catalog` tool. Settings use a separate custom format documented in `share/doc/files/settings-format.md`.

## Conventions

- Commits follow conventional-commits style (`feat:`, `fix:`, `refactor:`, etc.).
- For non-trivial changes, propose a short plan and wait for approval before editing.
- A production spec's public part holds only what production code calls (check_all's `Check_Test_Only_Api` refuses a public subprogram no source but its own unit names — by resolved name: written qualified or through a renaming, made direct by a use clause, bare in a child or subunit, or inherited by a type derived elsewhere; a word that is no call — a declaration, a parameter, component or object of that name, a named-association formal, a pragma's argument, a subprogram's `end Name`, or a bare word the source itself declares as an object or a subprogram of its own — names nothing; an overriding operation is called by dispatch and is exempt). A subprogram only the suite needs — a pure helper the unit uses internally, a hook, a report the tests read — is declared in the unit's private part and reached through a `*.Testing` child of that unit in `tests/tests/src` (whose body renames it; a child's visible part cannot see its parent's private part, so the child redeclares the profile). The exceptions are a unit's own interface that production happens not to call yet: `File_Types.Filetype_For_Extension`/`Icon_For_Filetype` (the lookups of the public map type) and `Leaf_Names.Length_Under` (the measure `Too_Long_Under` is defined by).
